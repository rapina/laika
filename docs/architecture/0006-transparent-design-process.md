# 0006 · 투명한 설계 과정과 공개 전 설계 검토

## 결정

게임 제작은 사람의 게임 디자인 과정을 모방한 순서로 진행하고, 그 과정 산출물을 공개한다.

1. 콘셉트 잠금 → `GDD.md` 작성 → 코드 시작 전에 GDD 기반 목표 화면 생성 → 목표 화면 기준 구현 → 실제 캡처와 대조.
2. 과정 산출물(설계 요약, 목표 화면, 실제 캡처, 대조 결과, 설계 검토)은 아케이드 작품 노트 페이지의 "제작 과정" 절에 한국어·영어로 공개한다. 카탈로그 필드는 `designProcess`다.
3. 공개 전에 제작과 맥락을 공유하지 않는 검토자가 `GDD.md`의 약속과 실제 빌드 플레이를 대조하는 설계 검토를 수행한다. 결과는 게임 저장소의 `design-review.json`에 남기고, 치명 갭이 있으면 공개를 차단한다. 공개 기록에서는 이 검토를 관제소의 거북이 체르파(`brand/CHERPA.md`)의 설계 검토로 표현한다. 무르는 공개된 전송만 플레이하는 인물이므로 공개 전 빌드를 보는 검토는 별도 인물이 맡는다. 한 인물이 설계 검토와 플레이 소감을 겸하면 첫 플레이 소감의 신선함이 성립하지 않는다(2026-07-18 페르소나 분리, 설탕실에 소급 적용).

## 이유

fluxforge(자속 대장간, No. 008)는 모든 자동 게이트를 통과하고 공개됐지만 사람에게는 게임이 성립하지 않았다. GDD는 흐르는 입자와 밴드별 이동 속도를 약속했지만 실제 화면은 정지 상태였고, 스와이프 길이를 피드백 없이 절대량으로 재현하라는 입력이라 화살표를 덧그리면 질 수 없고 자연스럽게 그으면 이길 수 없었다. 플레이 가능성 시뮬레이션은 내부 값으로 화면을 역산해 완전 정보 정책이 되었고, 완주율 하한만 검사하는 기준은 "질 수 없는 게임"을 오히려 통과시켰다.

세 가지 구조 문제가 겹쳤다.

- 설계 문서(GDD)와 실제 플레이의 갭을 대조하는 주체가 제작 에이전트 본인이었다.
- 과정 산출물이 게임 저장소 안에 흩어져 있어 사용자와 평가자가 갭을 볼 수 없었다.
- 평가(무르)는 공개 후 참고 의견이라 결함을 발견해도 출시를 막지 못했다.

과정을 공개하고 독립 검토를 공개 전 차단 게이트로 두면, 같은 갭이 출시 전에 잡히고 사용자도 "왜 게임이 이렇게 나왔는지"를 단계별로 확인할 수 있다.

## 운영 규칙

- 목표 화면은 `design/targets/`에 표준 이름(first-play, verb-<grade>, game-over)으로 커밋한다. 실제 캡처는 잠금 검증 캡처를 그대로 쓴다.
- 설계 검토자는 이전 대화를 받지 않는 별도 에이전트로 실행하고, 게임 저장소와 빌드 실행 경로만 받는다. 내부 상태 열람은 측정에만 쓰고 판단은 화면 정보로만 한다.
- 설계 검토는 실제 입력 경로(렌더된 화면 좌표에 대한 포인터·키 이벤트)로 사람 손 노이즈 모델 플레이를 포함해야 한다. 판정 함수 직접 호출만으로는 대체할 수 없다.
- 검토 산출물은 중립 findings(`design-review.json`)다. 체르파의 공개 문장(ko·en)은 잠금 뒤 서사 단계에서 findings를 바꾸지 않고 옮겨 적는다.
- 치명 갭(질 수 없음, 이길 수 없음, GDD 약속이 화면에 부재, 판정 관여 값의 은닉, 표시만 되는 가짜 스탯, 피드백 없는 절대량 입력)이 하나라도 있으면 verdict는 `blocked`이고 공개할 수 없다. 보완 후 재검토로만 해제한다.
- `designProcess`는 sequence 009부터 필수다. 기존 공개 게임은 소급 수정하지 않는다.
- 이 검토는 ADR 0004의 공개 후 플레이 평가를 대체하지 않는다. 설계 검토는 출시 게이트, 플레이 평가는 공개 후 소감이다.
