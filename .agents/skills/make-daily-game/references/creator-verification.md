# Creator verification

검증의 주인은 제작자다. 자신의 설계에서 무엇이 핵심 로직이고 어떤 결함이
가능한지 판단해 게임별 테스트를 작성한다.

## 필수

프로젝트에 실제로 존재하는 명령으로 다음을 수행한다.

1. GDD의 구체적 규칙과 로직을 검증하는 게임별 테스트 작성·실행
2. 첫 프로덕션 빌드와 sourceHash 기록
3. 새 맥락의 내부 플레이 관찰 뒤 게임 재제작
4. 게임별 테스트와 프로덕션 빌드 재실행
5. 현재 sourceHash를 기록하는 배포 스모크
6. 첫 실행의 `인트로 → 타이틀 → 게임 → 게임 결과` 순서와 결과 뒤 다시 시작

테스트 종류, 개수, 자동화 수준과 측정 방식은 정해 두지 않는다. 단위 테스트,
시뮬레이션, 브라우저 플레이, 이미지 비교나 수동 시나리오 중 게임에 맞는 것을
제작자가 선택한다. 결정론, 자동 완주, 특정 상태 형식과 공통 입력 시나리오는
요구하지 않는다.

`DAY.md`에는 각 테스트 명령이 어떤 설계 규칙을 확인하는지와 실제 결과를
기록한다. 확인하지 않은 것을 확인했다고 쓰지 않는다.

## 증거

- `smoke-result.json`은 최소한 `sourceHash`, `mounted`와 오류 목록을 기록한다.
- 게임별 테스트 결과는 제작자가 읽을 수 있는 형태로 저장하고 `DAY.md`에서
  명령과 대상 규칙을 연결한다.
- `production-playtest.json`에는 첫 구현과 최종 빌드의 서로 다른 sourceHash,
  빌드만 받은 플레이어의 관찰과 제작자가 반영한 변경을 기록한다.
- 캡처와 수치는 만든 경우에만 커밋한다.
- 소스나 필수 자산이 바뀌면 테스트와 배포 스모크를 다시 실행해 sourceHash를
  갱신한다.
