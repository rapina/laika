# Creator verification

프로젝트의 `package.json`과 실제 스크립트를 먼저 읽는다. 없는 명령을 통과한 것처럼 기록하지 않는다.

최소 검증:

```bash
npm test
npx tsc -b
npm run build:web
```

게임별 smoke와 viewport 검증이 있으면 함께 실행한다. 플레이 가능성 시뮬레이션(`creator-workflow.md`의 플레이 가능성 게이트)은 필수다.

```bash
npm run smoke
node scripts/viewport-smoke.mjs
node scripts/playability-sim.mjs
```

`scripts/playability-sim.mjs`도 템플릿에서 내려오는 정본이다. 하단 ADAPTER 절만 이 게임의 규칙으로 채우고, 공용 게이트 판정과 결과 결속은 그대로 둔다. 결과를 고정 경로 `verification/playability-result.json`에 `pass`·`sourceHash`와 함께 커밋한다 — 게시 게이트가 이 파일을 smoke sourceHash에 대조한다(sequence 17부터). 자리표시 어댑터는 채우기 전까지 실패한다.

`scripts/viewport-smoke.mjs`는 템플릿(`launchpad/scripts/`)에서 그대로 내려오는 정본이다. 뷰포트 4종을 단독 크기와 아케이드 포털 형상(상단 헤더 68px를 뺀 유효 높이) 양쪽으로 재서 캔버스 레터박스·해상도·넘침을 보고, 한국어와 영어 각각에서 게임 오버까지 진행시켜 결과 화면이 뷰포트 밖으로 잘리지 않는지 확인한다. 캡처는 `verification/`에 남는다. 갓 복제한 템플릿의 자리표시 게임은 레터박스 계약을 구현하지 않아 이 검사에 실패한다. 게이트 고장이 아니라 아직 게임이 없다는 뜻이니, 검사를 끄지 말고 게임 쪽을 맞춰라.

다음 동작을 실제 브라우저나 자동 플레이로 확인한다.

- 첫 화면에서 규칙 이해
- 핵심 동사 반응: 판정 등급별(정밀·성공·실패) 핵심 동사 직후 캡처를 남기고, 캡처만 보고 재료의 반응과 판정 등급을 답할 수 있는가. 세 캡처가 서로 구분되지 않으면 미달이다.
- 목표 화면 대조: 검증 캡처(첫 판, 핵심 동사, 게임 오버)를 GDD 뒤에 만든 목표 화면과 나란히 놓고 재료 질감·핵심 동사 반응·정보 요소가 목표 수준에 도달했는지 판정한다. 목표보다 눈에 띄게 빈약하면 미달이며, 의도적 차이는 `DAY.md`의 기록으로만 인정한다.
- 첫 판 가이드 3답: 첫 판 화면 캡처만 보고 ① 입력이 무엇을 하는지 ② 언제 행동하는지 ③ 목표와 종료 조건(횟수·실패 예산)을 답할 수 있는가. 캡처를 검증 기록에 남기고, 세 답을 캡처 옆에 적는다.
- 가이드 노출 규칙: 성공 2회까지 유지되고, 숨긴 뒤 실패 2회 연속이면 다시 나타나는가
- 성공과 실패 판정
- 게임 오버 2답: 게임 오버 화면 캡처만 보고 ① 판이 끝났는지 ② 어떻게 다시 시작하는지 답할 수 있는가. 재시작 안내는 화면 문구여야 하며, 캡처를 검증 기록에 남기고 두 답을 캡처 옆에 적는다.
- 종료 직후 잔여 입력이 결과 화면을 건너뛰지 않는가(보호 시간), 안내된 방법 그대로 실제 재시작되는가
- 한 판 전체 완주와 `game.manifest.json` 세션 상한 이내 종료
- 진행 중 시스템 반응이나 긴장 변화
- 일시정지 중 시뮬레이션 정지와 복귀 뒤 시간 안정성
- 음소거와 다시 켜기, 첫 입력 전 무음
- 재시작 뒤 초기 상태 복원
- 한국어와 영어의 기능·정보 일치
- 플레이 중 언어 변경 시 상태 유지
- 360×800, 390×844, 430×932 화면
- 넓은 화면(예: 900×760)에서 비율 유지 — 원형 요소가 원으로 보이고 캔버스가 uniform scale 레터박스로 맞춰지는가. 캔버스를 컨테이너에 `width/height:100%`로 늘리지 않는다.
- 대표 장면과 선택한 시각 매체의 식별성
- 콘솔 오류, 페이지 오류, 실패 요청 0건

자동 플레이는 개발 빌드의 결정론적 테스트 훅을 사용할 수 있다. 문구나 화면 좌표만으로 완료 여부를 추측하지 않는다.

브라우저 검증 주장은 커밋된 산출물로만 인정된다. 산출물이 없는 검증 문장은 미검증으로 취급한다.

- `npm run smoke`는 `smoke-result.json`에 실행 시점의 `sourceHash`를 기록한다. 잠금(`prepare-editorial.mjs`)이 현재 소스와 대조해 다르면 잠금을 거부하므로, 소스나 자산을 바꾸면 smoke를 다시 실행해야 한다.
- smoke는 화면에 그려진 UI가 아니라 실동작을 통과해야 한다: 게임 오버가 `__gameResult`를 호스트로 전달하고, 종료 화면을 화면 탭으로 눌러 새 판이 실제로 시작되는 것까지 관찰한다. 재시작 버튼을 그려 놓고 동작을 연결하지 않으면 여기서 실패한다.
- `smoke-result.json`, `smoke.png`, 뷰포트·첫 판 가이드·게임 오버 캡처는 저장소에 커밋한다. `.gitignore`에 넣지 않는다.
- DAY.md의 검증 문장에는 실행한 명령과 산출물 경로를 함께 적는다. 내부 상태를 읽어 프레임 정밀로 조작하는 봇의 성공 기록은 사람 기준 플레이 검증이 아니며, 플레이 가능성 게이트를 대체하지 못한다. `DAY.md`에 적는 모든 플레이 수치 주장(성공 횟수, 소요 시간)은 저장소에 커밋된 스크립트나 테스트로 재현 가능해야 한다.

다음 중 하나라도 남으면 제작 잠금을 만들지 않는다.

- 임시 자산이나 템플릿 문구
- 한국어·영어 누락
- 출처가 없는 게임 자산
- 결정론 테스트 실패
- 화면 넘침이나 브라우저 오류
- 캔버스 비율 왜곡(넓은 호스트에서 원이 타원으로 보임)
- 콘셉트 잠금과 다른 규칙, 세계 또는 대표 장면
- 진행 중 변화 없음: 판이 끝날 때까지 목표·위험·공간·리듬·판정이 모두 고정
- 핵심 동사의 반응이 오버레이 선·플래시·문구 수준(재료 무반응)이거나 판정 등급별 캡처가 구분되지 않음
- 목표 화면 부재(생성 도구가 있는 환경), 또는 검증 캡처가 목표 화면에 기록 없이 미달
- 첫 판 가이드가 세 질문(입력이 무엇을 하는지 · 언제 행동하는지 · 목표와 종료 조건) 중 하나라도 화면에서 답하지 못함
- 게임 오버 화면이 두 질문(판이 끝났는가 · 어떻게 다시 시작하는가) 중 하나라도 화면에서 답하지 못함
- 플레이 가능성 게이트 미달 또는 `scripts/playability-sim.mjs` 미커밋
- 플레이 가능성 시뮬레이션이 실제 스텝 함수를 틱 단위로 호출하지 않음(판정·시간을 닫힌 공식이나 상수로 재유도)
- `DAY.md`의 플레이 수치 주장에 재현 수단 없음
- `smoke-result.json` 부재, 실패 상태, 또는 `sourceHash` 불일치(소스 변경 뒤 smoke 미재실행)
- smoke 증거에 `gameResult` 없음(종료 결과 미전달) 또는 `restartVerified` 없음(화면 탭 재시작 미동작)
- 시각 매체 미달: 게임 화면이 단색 도형과 그라디언트 배치만으로 구성
- 생성 도구가 있는 환경에서 타이틀 키 이미지가 없거나 게임에 연결되지 않음
