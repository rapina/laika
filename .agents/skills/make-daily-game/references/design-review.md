# 설계 검토 게이트 (공개 차단)

제작 잠금 뒤, 라이카 제작 서사 전에 실행한다. 목적은 하나다: `GDD.md`가 약속한 게임과 실제 빌드에서 사람이 플레이하는 게임이 같은 게임인지 확인한다. 공개 기록에서는 이 검토를 관제소의 거북이 체르파의 설계 검토로 표현하지만, 검토 자체는 브랜드 중립으로 수행한다. 플레이 소감을 쓰는 지구의 고양이 무르와는 다른 인물이다.

## 독립성

- 검토자는 콘셉트·제작·관제와 이전 대화를 공유하지 않는 새 에이전트 맥락으로 실행한다.
- 전달하는 것: 게임 저장소 경로, 빌드 실행 방법(`npm run dev` 또는 dist 서빙), 이 문서.
- 전달하지 않는 것: 브랜드 문서, 과거 작품 노트, 제작 에이전트의 자기 평가.
- 제작 에이전트가 커밋한 시뮬레이션의 통과 출력은 증거로 인정하지 않는다. 검토자가 직접 실행하고 직접 플레이한다.

## 1. GDD 약속 대조표

`GDD.md`를 읽고 다음을 약속 목록으로 뽑는다. 각 약속을 실제 빌드 화면·코드에서 확인하고 `met / gap / fatal`로 판정한다.

- 콘셉트의 질문과 핵심 판타지(예: "흐르는 입자를 읽는다")가 화면에 실재하는가. 움직인다고 쓴 것은 실제로 움직여야 한다.
- 난이도 밴드가 있는 게임은 모든 변수가 지각 가능한가. 밴드가 없는 게임에는
  만들라고 요구하지 않는다.
- 판정식에 들어가는 모든 입력·보정치가 화면에서 읽을 수 있는가. 화면에 없는 값이 판정을 바꾸면 숨은 물리값이다.
- 화면에 표시되는 모든 수치·표식이 판정이나 결과에 실제로 관여하는가. 표시만 되고 아무 데도 안 쓰이는 스탯은 가짜 정보다.
- 첫 판에서 시작 방법과 안전한 첫 행동을 알 수 있는가. 종료·판정 등급이 실제로
  있는 게임만 게임 오버와 등급별 반응을 검사한다.
- `design/targets/`의 목표 화면과 실제 캡처가 재료·반응·정보 수준에서 같은 게임인가. 의도적 차이는 `DAY.md` 기록이 있어야 인정한다.
- **재료가 재료로 보이는가.** GDD가 말한 재료(물, 유리, 쇠, 실)의 질감이 실제 픽셀에 있는가. 게임의 주요 대상이 단색 도형으로만 그려져 있으면 시각 매체 미달이며, 콘셉트가 약속한 화면이 없는 것과 같다. gap으로 기록하고, 그 재료가 콘셉트의 핵심이면 fatal이다.
- **개발용 표시가 남아 있지 않은가.** 다음은 플레이어를 위한 정보가 아니라 만드는 사람을 위한 것이다. 하나라도 화면에 있으면 gap이고, 핵심 대상 위에 있으면 fatal이다.
  - 게임 대상에 그려진 배열 인덱스나 일련번호(`String(i+1)` 류)
  - 판정 영역을 그대로 드러낸 단색 원·사각형, 바운딩 박스, 와이어프레임, 좌표 격자
  - 픽셀·라디안·프레임 같은 내부 단위로 적힌 수치(교정 정보는 플레이어의 말로 적는다: "조금 더 왼쪽", "더 세게")
  - 내부 상태 덤프, FPS·시드·상태 이름 표시

## 1-2. 이기는 방법을 화면에서 배울 수 있는가

위 항목들은 전부 **값이 읽히는가**를 묻는다. 그것으로는 부족하다. sequence 13 「결 가르기」는 판정에 들어가는 모든 값이 화면에서 읽혔고, 독립 검토 두 번이 모두 그 사실을 옳게 인증했다. 그런데도 이 게임의 깊이 축 — 띠 근처에서는 일부러 정점을 비껴 쳐 전진을 아껴야 한다는 것 — 은 화면 어디에도 없었다. 화면 안내는 "초록 고리가 열릴 때 탭하세요"라고만 했고, 그것은 후반을 잃는 조언이다. 검토자는 여러 판을 실험해서야 진짜 전략을 찾았고, 찾은 뒤 성적이 두 배가 됐다.

**값이 읽히는 것과 전략이 배워지는 것은 다른 질문이다.** 규칙 안에만 있고 화면에 없는 깊이는 대부분의 플레이어에게 없는 것과 같다.

검토자는 다음을 답으로 적는다.

- 이 게임에서 **이기는 방법 한 줄**은 무엇인가. GDD가 깊이 축이라고 말한 것과 같은가.
- 그 방법을 **화면만 보고 알아낼 수 있는가.** 안내 문구, 재료 반응, 판정 피드백 중 무엇이 그것을 가르치는가. 짚을 것이 없으면 gap이고, 그것이 GDD가 내세운 깊이 축이면 **fatal**이다.
- 실기 플레이에서 그 방법을 **언제 알아냈는가.** 화면을 읽고 알았는가, 여러 판 실험해서 알았는가. 후자면 화면이 가르치지 못한 것이다.

## 2. 실기 사람 모델 플레이

실제 빌드를 브라우저에서 구동하고, **실제 입력 경로**(렌더된 화면 좌표에 대한 포인터·키 이벤트)로 플레이한다. 판정 함수 직접 호출이나 내부 상태 기반 입력 합성은 이 절을 대체할 수 없다. 내부 상태(`__gameState`)는 결과 측정에만 쓴다.

**문서화한 조작은 전부 눌러 본다.** `game.manifest.json`의 `controls`에 적힌 모든 항목(주 입력, 키보드, 재시작)을 각각 실제로 플레이하고, 그 결과를 대조표에 남긴다. 어느 하나라도 플레이하지 않으면 게시 게이트가 거부한다.

그중 특히 다음은 fatal이다. **어떤 입력도 게임을 대신 풀어 주지 않아야 한다.** 런타임이 내부에서 계산한 정답 벡터·정답 타이밍을 그대로 실행하는 입력이 있으면, 그 입력을 아는 순간 게임이 사라진다. 보조 조작(키보드 대체 입력)은 사람이 포인터와 같은 판단을 내려야 하고 같은 오차 여지를 가져야 한다. sequence 12는 문서에 적힌 키보드 조작이 자동 조준이어서, 그 키만 눌러도 매번 만점이 나왔다.

선택한 검증 프로필에 맞는 세 경로를 각 3회 이상 실행한다. 아래 세 프로필은
`challenge` 게임의 기본값이며 다른 프로필은 GDD의 선택·탐색·구성 경로로
대체할 수 있다.

1. **직관**: 첫 판 가이드가 가르치는 그대로. 반응 지연 ~N(200ms, 40ms), 각도 오차 ~8°, 거리·타이밍 오차 ~15%.
2. **숙련**: GDD가 의도한 요령을 아는 플레이. 오차는 직관의 절반.
3. **자연 제스처**: 안내를 정독하지 않은 플레이어의 관성적 입력(평범한 스와이프 길이·연타·성급한 타이밍). 첫 실패 뒤 화면의 교정 정보만 보고 다음 시도를 수정한다.

**하네스를 새로 짜지 않는다.** 게임 저장소의 `scripts/play-harness.mjs`가 브라우저 구동, 손떨림 노이즈, 병렬 실행, 자체 점검을 이미 갖고 있다. 게임마다 다른 것은 `act`(한 번의 입력을 어떻게 넣는가)와 `readState`(화면 상태를 어떻게 읽는가) 둘뿐이므로 그 둘만 쓴다. 매번 다시 짜면 시간도 들고, 노이즈 모델이 조용히 눌리는 사고가 반복된다.

```js
import { runProfiles } from './play-harness.mjs'

const out = await runProfiles({
  url: (seed) => `http://127.0.0.1:4188/autoplay.html?seed=${seed}`,
  profiles: [
    { name: 'intuitive', runs: 3, angleSigmaDeg: 8, magnitudeSigma: 0.15, reactionMs: [200, 40] },
    { name: 'skilled',   runs: 3, angleSigmaDeg: 4, magnitudeSigma: 0.075, reactionMs: [200, 40] },
    { name: 'natural',   runs: 3, angleSigmaDeg: 12, magnitudeSigma: 0.25, reactionMs: [260, 60] },
  ],
  concurrency: 3,
  readState: () => globalThis.__gameState ?? null,
  async act({ page, state, noise, box }) { /* 게임의 입력 하나 */ },
})
```

검토 하네스 자체 점검: 사람 모델에 넣은 오차가 실제로 그만큼 나오는지 먼저 확인한다. `runProfiles`가 돌려주는 `selfCheck`에 프로필별 `angleRatio`·`magnitudeRatio`(지정 대비 실측 표준편차)와 `sound`가 들어 있다. `sound`가 거짓이거나 비율이 1에서 크게 벗어나면 하네스 결함이며, **그 상태의 관측치로 판정하지 않는다**(오차가 15%에서 1.5%로 눌린 채 돌아 "질 수 없음"을 낼 뻔한 사건이 있었다). 이 값을 `design-review.json`의 `method`에 적는다.

통과 기준은 GDD에 선언한 검증 프로필을 따른다.

- `challenge`에서는 직관이 핵심 판정을 경험하고 숙련이 완주 가능하며 두 경로의
  결과가 구분된다.
- `puzzle`, `strategy`, `construction`에서는 선택·순서·배치가 다른 상태를 만들고
  최소 한 경로가 목표 상태에 도달한다.
- `exploration`, `toy`에서는 서로 다른 입력 시퀀스가 구분되는 반응을 만들고
  언제든 안전하게 초기화할 수 있다.
- **질 수 없음 검출**은 도전을 약속한 게임에만 적용한다.
- **무입력 검출**은 자동 진행과 실패를 약속한 게임에만 적용한다. 퍼즐·탐색·
  장난감이 입력 없이 기다릴 수 있다는 이유로 막지 않는다.
- **이길 수 없음 검출**: 자연 제스처 프로필이 화면 교정 정보를 따라 수정해도 회복 경로 없이 반복 즉사하면 fatal.
- 절대량 재현 입력(스와이프 길이·유지 시간 같은 연속량)이 판정에 쓰이면, 제스처 중이나 직후에 그 양이 화면에 실시간 표시되어야 한다. 표시 없는 절대량 재현 과제는 fatal.
- **등급 사다리 검사**: 게임에 등급·칭호·정밀 카운터가 있으면 두 가지를 본다. 제작 측 시뮬레이션 수치로는 이 검사를 대체할 수 없다.
  1. **사다리가 살아 있는가.** 관측한 판에서 최저 등급 위로 올라간 판이 하나라도 있어야 한다. 모든 관측 판이 최저 등급에 머물면 그 사다리는 죽은 축이다. 임계값이 실기가 아니라 자체 시뮬에 맞춰진 것이며, 실기 분포 위로 보정한 뒤 다시 검토한다.
  2. **등급이 플레이 중에 화면에 있는가.** 등급은 **발동하는 순간 그 이름으로 불려야** 한다. 결과 화면에서 `정타 48회`라고 세어지는데 플레이 중에는 `정타`라는 말도 그에 대한 반응도 없으면, 플레이어는 무엇을 잘해야 등급이 오르는지 화면에서 배울 수 없다. 이것은 sequence 11과 13에서 **두 번 나온 결함**이고, 11의 학습이 산문으로만 남아 13에서 그대로 재발했다.

  결과를 `gradeLadder` 블록에 적는다(§3). 등급이 없는 게임은 `{"present": false}`로 명시한다. 게시 게이트(`scripts/lib/publication.mjs`의 `verifyGradeLegibility`)가 sequence 14부터 이 블록을 강제하고, 죽은 사다리와 결과 화면 전용 등급을 거부한다.

- **캡처가 담은 순간을 의심한다.** 핵심 동사 증거(`verb-*`)는 반드시 **렌더된 상태를 관측해서** 찍혀야 한다. 고정 지연으로 찍으면 안 된다. 드라이버 왕복이 수백 ms라 지연은 해소 순간을 넘기고, 그렇게 찍힌 프레임은 틀렸다고 알리지 않은 채 **다음 판**을 담는다. sequence 13이 정확히 이것으로 재료 반응 미달을 공개까지 내보냈고, 설계 검토 두 번이 그 증거를 보고 pass를 냈다.

  검토자가 할 일: 판정한 프레임이 정말 그 판정의 순간인지 확인한다. debug state의 렌더 진행 필드(예: 그려진 진행도)가 판정에 쓰인 값에 도달해 있어야 한다. 두 값이 어긋나면 증거가 무효이고, 그 증거로는 통과시키지 않는다. 게시 게이트(`scripts/lib/capture-timing.mjs`)가 sequence 14부터 고정 지연 캡처를 거부하지만, **기다린 상태가 옳은 상태인지는 기계가 판단하지 못한다.** 그 부분이 검토자의 몫이다.

## 3. 산출물: design-review.json

게임 저장소 루트에 커밋한다. 중립 문체, 한국어 요약과 영어 요약 포함. **아래 필드 이름을 그대로 쓴다.** 스키마를 새로 지어내면 게시 게이트가 거부한다. 특히 `claim`을 빼고 관측만 적으면 대조표가 성립하지 않는다. 실제로 그렇게 통과한 게임이 있었고, 그 게임은 표적이 개발용 원반으로 그려진 채 공개됐다.

```json
{
  "schemaVersion": 1,
  "reviewedAt": "YYYY-MM-DD",
  "sourceHash": "<smoke-result.json과 같은 방식으로 계산한 소스 해시>",
  "verdict": "pass | blocked",
  "method": {
    "build": "<플레이한 빌드 경로>",
    "inputPath": "pointer-events",
    "inputPathsExercised": ["primary", "keyboard", "restart"],
    "profiles": ["intuitive", "skilled", "natural-gesture"],
    "runsPerProfile": 3
  },
  "promises": [
    { "id": "p1", "source": "GDD.md#코어-루프", "claim": "…", "observed": "…", "status": "met | gap | fatal" }
  ],
  "playObservations": [
    { "profile": "natural-gesture", "runs": 3, "completions": 1, "note": "…" }
  ],
  "strategyLegibility": {
    "winningStrategy": "<이기는 방법 한 줄>",
    "taughtOnScreen": true,
    "taughtBy": "<그것을 가르치는 화면 요소. 없으면 빈 문자열>",
    "learnedFrom": "screen | experiment"
  },
  "gradeLadder": {
    "present": true,
    "names": ["<최저 등급>", "…", "<최고 등급>"],
    "lowestObserved": "<실기에서 관측한 최저 등급>",
    "bestObserved": "<실기에서 관측한 최고 등급>",
    "shownDuringPlay": true,
    "shownBy": "<발동 순간 등급 이름을 부르는 화면 요소>"
  },
  "idleRun": {
    "ran": true,
    "survivedFraction": 0.27,
    "note": "<무입력으로 어디까지 갔는지, 정밀 판정을 얻었는지>"
  },
  "fatalGaps": [],
  "summary": { "ko": "…", "en": "…" }
}
```

- `promises`의 각 항목은 `id`, `source`, `claim`, `observed`, `status`를 모두 채운다. `claim`은 GDD가 약속한 문장, `observed`는 실제 빌드에서 본 것이다. 게시 게이트(`scripts/publish-game.mjs`)가 빈 값을 거부한다.
- `sourceHash`가 현재 `smoke-result.json`의 값과 다르면 검토는 낡은 것이며 무효다.
- `fatal`이 하나라도 있으면 `verdict: "blocked"`. blocked 상태에서는 라이카 서사·릴리스·공개를 진행할 수 없다.
- blocked 처리: 관제가 findings를 제작 사이클로 되돌린다. 수정은 잠금 뒤 수정 사이클(테스트·smoke 재실행 → 재빌드 → 픽스처 재동기화 → lock 갱신 → DAY.md 기록)을 따르고, 수정 뒤 새 검토자 맥락으로 재검토한다.
- `gap`(치명 아님)은 공개를 막지 않지만 findings에 남기고, 공개되는 designProcess와 `docs/knowledge/PLAYER_FEEDBACK.md` 중립 학습에 반영한다.

## 공개 반영

verdict와 무관하게 findings는 수정하지 않는다. 잠금 뒤 서사 단계가 `summary`와 주요 promises를 체르파의 공개 문장(ko·en)으로 옮겨 적어 카탈로그 `designProcess.review`에 등록한다. 옮겨 적기는 어조 변환만 허용하고 판정을 바꿀 수 없다.
